# AI 产品经理知识体系

当前版本以「选场景 → 设计任务 → 接入与执行 → 评测上线」为项目主线。四个阶段分别产出场景简报、任务规格、可运行原型和试点上线方案。用同一个真实场景贯穿全程，在交付物卡片里保存成果摘要或链接。

首页推荐、聚焦方向和自动周计划围绕 18 个项目动作。旧版 63 项可在「项目地图 → 资料库」查阅，原打卡、笔记和周计划继续按旧 ID 读取。新项目进度单独统计，导入导出与多端同步沿用现有数据格式。

以下 v2 设计记录保留作历史参考；当前运行、数据与同步机制见后续章节。

> 一个把「学到哪了」换成「今天做什么」的学习系统。
> 单文件应用，无构建、无后端，双击 `index.html` 即可运行。

## 一、为什么有 v2：v1 的问题诊断

v1 是一张 63 个知识点的**打卡地图**：点卡片标记「已掌握」，配一个总进度环。
实际使用结果是——**打开就关掉，从来没真正下手过**。

这不是自制力问题，是**产品的动作错位**。v1 有三个结构性缺陷：

### 1. 唯一的交互是「结果确认」，不是「开始学习」

「机器学习核心概念」「RAG」「Agent」「增长黑客」……每一项都是 10–50 小时的工程，
不是一个可执行动作。页面既没给第一步做什么，也没给资源和验收标准。

于是打开应用时，你只有两个选择：

- 承认自己不会 → 关掉
- 打勾 → 自欺

**真正的摩擦（去哪学、学什么、怎么算学会）全在应用之外**，
应用只负责最后那一下打勾。所以 v1 的「下一步建议」给的是「机器学习核心概念」
——按数组顺序取的第一个未完成项，既不是最该学的，也不是今天能动手的。

### 2. 进度二元化，且没有时间维度

只有 done / not-done，没有中间态。真实学习是 0 → 30% → 70%，
中间态无处安放 —— 所以前两周无论多努力，总览永远显示 **0%**。
那个 96px 的大圆环写着 0%，是**负反馈而不是正反馈**。

同时「知识地图」和「冲刺/周目标」是两套互不相通的数据：
周目标要你凭空手写，地图不会自动流入；习惯 KPI 统计的是「打卡天数」，
而打卡本身又需要先学会 —— 死循环。

### 3. 首次使用摩擦过大

第一屏就要求配置 GitHub PAT 才能多端同步。把最具摩擦的技术配置放在最前面，
等于在门口先砌一道墙。而且以 63 项为分母的完成度，视觉上永远贴近 0。

## 二、v2 的设计对策

| v1 的问题 | v2 的对策 |
|---|---|
| 知识点是「学科名」，无法动手 | **63 个知识点各自配了「第一步动作 / 验收标准 / 搜索关键词 / 权威入口 / 预估时长」**，动作小到一次坐下就能做完 |
| 打勾前提是「已学会」 | 打开首页第一眼就是 **「▶ 现在开始 25 分钟」**，一次点击即进入专注计时 |
| 只有 done / not-done | **三态：未开始 / 学习中 / 已掌握**，学习中计 0.5 分，中间态也算进度 |
| 总览永远 0%，是负反馈 | 首页 **不再展示总百分比**，改为「今天推进 0/1 项」+ 连续天数 + 本周专注分钟。长期刻度收进侧栏和「我的」，并明确标注「慢是正常的」 |
| 地图与周计划割裂 | **「✨ 从地图挑 3 个」一键把知识点排进本周**；推荐算法优先推「学习中」的项，并按三大支柱轮转 |
| 云同步挡在门口 | 云同步**降级**为「我的 → 可折叠的高级选项」，本地 localStorage 单独可用 |
| 无中间反馈 | **专注计时器**：结束自动记为「学习中」+ 记录分钟数 + 系统通知 |

### 核心机制：一个 25 分钟的闭环

```
打开应用  →  首页已经替你选好了下一个动作
          →  点「开始 25 分钟」
          →  计时结束，自动标记「学习中」，写一句收获
          →  今日目标达成 → 「可以收工了」
```

**门槛低到你没有理由拒绝，才是能坚持的设计。** 每天只要 1 个动作，
超额不算绩效，休息也是进度。

## 三、推荐逻辑：它按什么顺序推给你

首页那个「现在做这个」不是随机的，也不是简单地按目录顺序。
`candidates()` 先把「学习中」的项排最前（按最近动过的时间倒序，让你接着做完手头这件），
其余项按**四层权重做稳定排序**：

| 权重 | 条件 | 含义 |
|---|---|---|
| **8** | 前置依赖已满足 | 学习路径。缺失前置的项一律沉底 |
| **4** | 属于你选的「聚焦方向」 | 让推荐听你的 |
| **2** | 已排进本周 | 手动排入的项优先 |
| **1–2** | 时长短于当前预算 | 18 分钟的空档不推 90 分钟的活 |

权重 8 > 4+2+2，所以**「依赖没满足」的项一定排在所有「依赖已满足」之后**。
同权重时保持「三大支柱轮转」的基准顺序（硬实力 → 软实力 → 实践 → …），
避免连着三次都在啃硬实力。

### 前置依赖（可关闭）

63 个知识点之间有 34 条依赖关系，例如：

```
机器学习核心概念 → 深度学习与神经网络 → LLM 原理与能力边界 → Prompt Engineering
                                                        ├→ RAG 检索增强生成 → 【实战项目】
                                                        └→ Agent 智能体
```

判定标准是前置项达到**「学习中」而非「已掌握」** —— 否则一次没学透就会把整条路径堵死。

**这只是推荐顺序，不是门禁。** 地图里随时可以直接开始任何一个知识点，
卡住前置的卡片上会标 `🔒 先学 X`，点开也会说明。想彻底关掉，
去「我的 → 推荐顺序 → 按前置依赖排序」。

### 聚焦方向

在「我的 → 聚焦方向」里选 1–2 个知识组（如「大模型与生成式 AI（核心）」），
推荐会把它们排到前面。最多选 2 个 —— 选 5 个就不叫聚焦了。

这里有个交汇情况：如果你聚焦的方向**整块都还在等前置**，光加权重是没用的
（因为依赖权重更高）。所以此时首页会显式说明：

> 🎯 聚焦方向「大模型与生成式 AI（核心）」整块都还在等前置，所以现在推给你的还是别的方向。
> 但只要先做掉 **机器学习核心概念**，这条路就会打开。　`[把它加入本周]`

提示点名的是**沿依赖链走到底、现在真的能动手的那个根节点**，
而不是中间那些本身还被卡住的项。

### 时长自适应

首页焦点卡上有「现在有 __ 分钟」：15 / 25 / 45 / 60+。

- 这个选择**同时决定计时长度**和**推荐排序**。
- 预算越小越优先推短动作；**预算 ≥60 视为「时间充裕」，不再干预顺序**。
- 如果当前动作比预算长，会直说：「这项完整做约需 45 分钟。今天先做 25 分钟也算推进。」
  计时器仍按你的预算走，剩下的明天接着来。

最短的动作是 30 分钟 —— 所以选 15 分钟时会优先推那批 30 分钟的轻量动作，
并在卡片上说明。应用不会假装 15 分钟能做完 45 分钟的事。

### 它会告诉你为什么

排序规则再多，如果用户看不到，就等于不存在。所以焦点卡上有一行
**「💡 为什么是它」**，把当前这一项的四层权重摊开成一句人话：

> 💡 **为什么是它**：这项没有前置，可以直接开始 · 约 30 分钟，比 25 分钟略长，但已是最短的一档
> （待推进的 62 项里排第 1，同时满足的有 5 项）

几种典型形态：

| 情况 | 说明 |
|---|---|
| 没有前置 | 「这项没有前置，可以直接开始」 |
| 前置已满足 | 「前置已就绪（深度学习与神经网络）」 |
| 前置缺失 | 「**还有前置没开始**：机器学习核心概念」 |
| 命中聚焦 | 「属于你的聚焦方向「数据能力」」 |
| 已排本周 | 「你已把它排进本周」 |
| 时长合适 | 「约 45 分钟，在你的 45 分钟预算内」 |
| 时间充裕 | 「你选了「时间充裕」，所以不按时长筛」 |
| 正在推进 | 「你已经开始了这一项，做完比开新的更划算」 |

脚注还会给出**名次和并列数**：「待推进的 62 项里排第 1，同时满足的有 5 项」——
这句话顺带解释了「换一个」到底做了什么：它只是沿着这个排名往下走一位。

这行说明由 `whyFocus()` 生成，它读取的是 `candidates()` **排序时实际算出的权重缓存**
（`_rank`），而不是另写一份判断逻辑。这样解释和排序不可能各说各话。

几个刻意的取舍：

- **明显超预算时不在这里重复说明**，因为卡片下方已有专门的「今天先做 N 分钟也算推进」提示。
- **并列时如实说「同时满足的有 5 项」**，而不是编一个「最合适」的理由。
  那 5 项确实条件相同，最终先后就是支柱轮转，没必要粉饰。

## 五、多端适配

按**手机 + iPad 优先**设计，三档断点：

| 断点 | 布局 | 导航 |
|---|---|---|
| `< 600px` 手机 | 单列卡片、底部安全区适配 | 底部标签栏（含角标） |
| `600–1023px` iPad 竖屏 | 2 列卡片、4 列统计 | 底部标签栏 |
| `≥ 1024px` iPad 横屏 / 桌面 | 左侧固定侧边栏 + 正文限宽 860px | 侧边栏（含计时器与主题开关） |

已验证：**在真实 390px 宽度下四个页面横向溢出元素 = 0**。

- `viewport-fit=cover` + `env(safe-area-inset-*)`，适配刘海屏与底部横条
- 知识点详情在手机上是从底部升起的**抽屉**，在平板/桌面是居中弹层
- 触控目标均 ≥ 40px，`@media(hover:hover)` 隔离悬停态避免触屏残留
- iOS 可「添加到主屏幕」，`sw.js` 提供 network-first 离线缓存

## 六、数据与多端同步

### 存储布局

数据默认只存在本设备浏览器，**不配置任何东西也能正常用**。

| localStorage 键 | 内容 |
|---|---|
| `aippm_progress_v1` | 知识点记录 `{st, sts, note, nts, ts}` |
| `aippm_plan_v2` | 周计划：`items` 时刻表 + `goals` 映射 + 复盘 |
| `aippm_days_v1` | 有实质推进的日期（连续天数） |
| `aippm_sessions_v1` | 专注记录 `{uid, id, min, ts}` |
| `aippm_settings_v1` | 每日目标 / 每周动作数 / 专注时长 / 聚焦方向 |
| `aippm_reset_v1` | 「清空全部数据」的时刻 |
| **`aippm_sync_v1`** | **同步配置 `{owner, repo, path, token}`** |
| `aippm_sync_meta_v1` | 上次成功 / 失败时间与原因 |

### 安全边界（不可妥协）

静态托管页面无法安全持有密钥 —— 公开页面上的任何东西都是公开的，
带写权限的令牌写进代码等于把私有仓库的写权限交给所有访问者，
而且 GitHub 的机密扫描会直接吊销公开仓库里的 PAT。

所以：

- 代码里**只内置** `owner/repo/path`，**绝不内置 token**；
- token 只存**每台设备**的 `aippm_sync_v1`，从不进入同步载荷与导出文件
  （`test.html` 与 CDP 测试都有断言锁住这一点）；
- 数据仓库 `KaraChenDS/ai-pm-progress` 是 **private**，代码仓库可以 public；
- 令牌用 **Fine-grained PAT**：只勾那一个数据仓库，权限只给 **Contents: Read and write**。

### 合并策略：分层，而不是「整条记录取较新」

整条覆盖是这类同步最容易犯的错：两台设备各改同一条记录的不同部分时，必然丢一边。
这里按字段各带自己的时间戳：

| 数据 | 合并方式 |
|---|---|
| 知识点状态 `st` | 按 `sts` 取较新；「取消掌握」就是较新的 `st=0`，天然可同步 |
| 知识点笔记 `note` | 按 **自己的** `nts` 取较新，与状态互不干扰；同时发生时不拿空值抹掉内容 |
| 周动作 `items` | `{id: 时刻}`，**正数=排入，负数=移除墓碑**，`mergeByTime` 取绝对值大的 |
| 周目标 `goals` | 按 id 并集，同一 id 取较新版本；删除写 `del:true` 墓碑 |
| 周复盘正文 | 按自己的 `reflectionAt`，同样不让空值覆盖 |
| 专注记录 | 按 `uid` 去重并集 |
| 日期集合 | 并集 |
| 设置 | 整对象按 `settingsAt` 取较新 |
| 「清空全部数据」 | `resetAt` 取最大，比它旧的记录一律丢弃 —— 否则清空会被另一台设备推回来 |

**推送前先合并云端。** 这一条是必须的：推送发送的是整个文件，
如果本机停留在旧状态（例如防抖推送晚于另一台设备的写入），
整文件覆盖会把对方的新数据抹掉。所以 `syncPush` 会先 `GET` → 合并进本机 → 再 `PUT`，
合并后本机是超集，写回一定安全。这个问题是被 CDP 测试抓出来的。

### 自动触发

| 时机 | 动作 |
|---|---|
| 应用启动 | 静默拉取合并 |
| 任何改动 | 防抖 2.5 秒后静默推送 |
| 切回前台 / 窗口获得焦点 / 恢复联网 | 再拉一次 |
| 云端 404 | 用本机数据创建（首次引导） |
| 顶栏 ☁️ 胶囊 | 手动立即同步 |

**但不会「静默到无法诊断」**：失败时首页顶部出现可重试的横幅，
`我的 → 多端云同步` 里显示上次成功/失败时间与原因。

### 网络诊断

**网络故障与令牌故障必须给不同文案**，否则用户会把网络问题当成令牌配错：

- 连不上：`连不上 api.github.com —— 网络被限制或需要代理，不是令牌问题`
- 令牌无效：`令牌无效或已过期（HTTP 401）`
- 权限不足：`权限不足或触发限流（HTTP 403）`
- **写入被拒：`令牌看不到这个仓库，写入被拒（HTTP 404）`**

### ⚠️ 关于 404：这条最容易误导人

**Fine-grained 令牌如果没勾选某个仓库，GitHub 返回的是 404 而不是 403** ——
它不告诉你私有仓库是否存在，以免泄露。

所以「404」在写入语境的真实含义几乎总是**令牌权限问题**，而不是「仓库不存在」。
应用现在会区分这两种语境，并在错误提示里直接给出下一步：

> Fine-grained 令牌如果没勾选这个仓库，GitHub 会返回 404 而不是 403。
> 请检查令牌的 Repository access 是否包含 `<owner>/<repo>`，权限是否为
> `Contents: Read and write`。

「🩺 诊断」按钮逐环节报告：配置 → 能否访问 `api.github.com`（拿到任何响应都算通）
→ 令牌是否有效 → **令牌能否看到这个仓库（决定性的一步，并检查 `permissions.push`）**
→ 数据文件。第 ④ 步会直接停住并说明原因，不会让你继续往下猜文件不存在。

> **中国大陆网络注意**：`github.io` 能打开 ≠ `api.github.com` 能通，两者常被分别处理。
> 先用手机 Safari 直接打开 `https://api.github.com/` 确认；不通就挂代理，
> 或把同步层换成 Gitee（协议相同，改动约 30 行）。

### 新设备一键连接

在已连接的设备上点「🔗 复制新设备连接链接」，得到
`https://<站点>/#t=<token>`，在手机/iPad 上打开即自动完成连接，
随后地址栏里的令牌会被立刻抹掉（`history.replaceState`）。

⚠️ 这条链接会留在聊天记录里 —— 用完即弃更稳妥，或者直接手动粘贴令牌。

## 七、本地运行与部署

```bash
# 本地预览（Service Worker 需要 http(s)，file:// 下会自动跳过）
python3 -m http.server 8912 --bind 127.0.0.1 --directory .

# 打开 http://127.0.0.1:8912/
```

App 已部署在 **https://karachends.github.io/ai-pm-knowledge/**：

```bash
git push origin main        # Pages 自动重建，约 1 分钟生效
```

Service Worker 对 HTML 导航使用 `cache: "no-store"` —— GitHub Pages 给 HTML 设了
`max-age=600`，不绕开的话推送新版本后最长 10 分钟仍可能拿到旧页面。

所有资源路径都是相对的（`icons/`、`manifest.webmanifest`、`sw.js`、`start_url:"./"`），
所以放在 `/<repo>/` 子路径下不用改任何东西。

> 局域网 `http://` 不是安全上下文，Service Worker 不会注册 ——
> 「添加到主屏幕」能装但**不能离线**。要真正离线必须走 HTTPS。

## 十、已知限制

- **权威入口是搜索链接**，不是课程直链 —— 这是刻意的：搜索词不会像课程链接那样过期。
- **周计划跨周不自动滚入**，需要你在首页横幅点一次「滚入本周」（刻意保留人工确认）。
- **计时器依赖页面存活**，切到后台时靠系统通知提醒；iOS Safari 在极端省电模式下可能不触发。
- **前置依赖是我人工定义的**（34 条），不是从数据里推导出来的。你可以直接改
  `index.html` 里的 `PREREQ` 表来调整成自己的路径。
- **没有间隔复习**：标记「已掌握」后该项不会再回到推荐队列。这一条是刻意没做的，
  因为复习调度会显著改变「每天一个小动作」的轻量手感。

同步相关的限制（诚实列出）：

- **设置是整对象按 `settingsAt` 取较新**，没有逐键合并。如果你恰好同时在一台设备改
  「每日目标」、在另一台改「专注时长」，会丢一边。设置改动频率极低，没做逐键合并。
- **「清空全部数据」是全局的**：`resetAt` 会丢弃所有早于它的记录，包括另一台设备上
  可能还没同步上来的内容。清空后请让各设备都同步一次。
- **不做二进制/照片同步**：只同步一份 JSON 状态，几 KB 级别。
- **`api.github.com` 在部分网络下不可达**，而 `github.io` 可能照常打开。
  「🩺 诊断」会明确区分这两种情况；真的不通只能挂代理或改用 Gitee。
- **每台设备要连接一次**（粘贴令牌，或用 `#t=` 链接），这是安全设计的必然代价 ——
  令牌不能写进代码。
- **令牌泄露后的处理**：直接去 GitHub 吊销那个 Fine-grained PAT 即可，
  数据本身不受影响（令牌只在那一个仓库有 Contents 权限）。
